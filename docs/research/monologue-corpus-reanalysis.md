# 수집 자료 기반 혼잣말 재분석

## 결론
혼잣말 소스 번역·실행 기능은 구현 가능하며, 이번 자료는 실제 호환 대상을 정하고 회귀 테스트를 만들기에 충분히 유용하다. 다만 단순한 C 유사 파서와 명령 전송만으로는 부족하다. 갈무리 문서형 소스 가져오기, 문자열 감지 상태, 버전별 include 해석, 부분 전송이 필수다. 기존 SCF 직접 실행 및 원본과 같은 SCF 생성 가능성은 여전히 별도 분석 대상이다.

이번 작업은 정적 조사다. 수집한 스크립트와 설치 프로그램을 실행하지 않았고 게임에 명령을 보내지 않았다. 원본 및 앱 제품 코드를 수정하지 않았다.

## 조사 범위와 확정 수치
G:\퇴마요새 전체 파일 목록과 하위 폴더를 조사했다. ZIP 8개는 목록을 확인했고 압축 내부의 모든 파일을 별도로 중복 집계하지 않았다.

| 항목 | 결과 |
|---|---|
| SCS 확장자 | 130개 |
| 실제 일반 조합형 텍스트 | 50개 |
| 일반 CP949 텍스트 | 1개 |
| KSR Galmuri 문서형 소스 | 78개 |
| SCS 확장자의 SCF 바이너리 | 1개 |
| 실제 소스 129개 중 SHA256 중복 제거 | 101개 |
| H 헤더 | 5개, 내용 기준 3종 |
| SCF 확장자 | 40개 |
| CHM | 3개, SHA256이 모두 같음 |
| PDF | 3개: 61쪽 매뉴얼, 1쪽 지도 2개 |

초기 인코딩 추정에서는 문서형을 CP949로, 바이너리 한 개를 조합형으로 잘못 분류했다. 파일 헤더와 내부 레코드를 확인한 후 위와 같이 교정했다. 확장자와 키워드 점수만으로 소스를 판정해서는 안 된다.

## 1. 소스 파일 가져오기 방식의 변경
78개는 `(c) KSR Galmuri File 1,0` 헤더를 가진다. 일반 UTF-16도 아니며, 문서 레코드 안의 16비트 값에서 ASCII는 하위 바이트, 한글은 조합형 코드로 읽는 방식으로 소스 문장을 추출했다. 대표 파일의 include, 함수, 경로 배열, 문구 감지 문자열이 정상적으로 복원된다.
연구용 추출기는 관찰된 레코드 구분 패턴을 이용한다. 모든 서식/손상 파일에 대한 완전한 문서 파서라고 주장하지 않는다. 제품 가져오기 구현에서는 길이 검증, 레코드 경계, 손상 경고 및 미리보기가 필요하다.

`MUD\MUD\퇴마요새\혼잣말\카타콤브1층(사번)-페이.SCs`는 Script File 헤더를 가진 이미 번역된 바이너리다. SCS 이름만 보고 다시 번역하려 해서는 안 된다.

## 2. 대기 함수만으로는 사냥 스크립트를 지원할 수 없음
핵심은 다음 상태 있는 API다.
- 찾을글(문구 목록): 감지할 문구들을 등록.
- 찾은글번호(): 감지된 문구 번호를 확인해 분기.
- 찾은글정리(): 감지 상태를 비움.
- 글마중/제한글마중/글마중제한시간: 수신 대기 및 제한 시간.

중복 제거한 소스와 헤더 104개에 대한 주석·문자열 제외 근사 검색에서 찾을글/찾은글번호/찾은글정리는 각각 59개 파일에 나타났다. 보내기/지연은 각각 79개, 정수보내기 57개, 제한글마중 36개, 글마중 17개다. 이 수치는 구문 분석기 결과나 실행 호환율이 아니다. include에서 정의된 공통 함수 호출은 실제 내장 함수와 별도 구분해야 한다.

실제 예: NO_SKILL.H는 `혼이`쓰러졌다` 같은 패턴을 등록하고 번호 1을 몹 사망으로 처리한다. 목록의 공백과 백틱은 원본의 패턴 표현으로 보이며, 단순 문자열 일치로 대체하면 안 된다. 백틱의 정확한 의미, 여러 패턴 동시 일치 시 우선순위, 찾은글번호의 소비 여부와 정리 범위는 원본으로 비교 확인해야 한다.

## 3. 헤더는 버전과 원래 폴더를 보존해야 함
- NO_SKILL.H 2개는 같은 내용.
- USE_SKILL.H는 V1.0과 V1.1이 다름.
- V1.1 폴더의 USE_SKILL1.0.H는 이전 버전 보관본과 내용이 같다.
- 소스들의 include에는 I.H, ENGLISH.H, NO_SKILL.H, USE_SKILL.H가 나온다.
- I.H/ENGLISH.H는 이 수집 폴더의 독립 파일 목록에 없지만 기존 C:\KSR\MULTI\SCF에서 확인했다.

V1.1 README는 정신력 관련 대기 상태와 신수훈련/방어기술 처리 수정 사항을 설명한다. 따라서 USE_SKILL.H를 하나로 통일하거나 최신 버전으로 조용히 교체하면 안 된다. 소스 폴더와 해당 배포본 루트를 기준으로 해결하고 어떤 헤더를 선택했는지 표시해야 한다.
이전에는 NO_SKILL.H만 있어 진입 프로그램이 부족했지만 이번에는 평타/스킬 사냥의 실제 진입 소스들이 확보되었다.

## 4. 언어와 런타임 요구사항
- 한국어 키워드, 영어 별칭, include/define, 전역/지역 변수, 문자열 배열, 사용자 함수, 함수 선언, 조건/반복/break, 산술·비교·논리 및 복합 대입.
- strcat은 반환값을 대입하지 않고 대상 변수를 변경하는 형태다. 일반 JavaScript 문자열 함수로 단순 치환하면 안 된다.
- 창문글월받기는 이름 등을 인자로 전달한 변수에 넣는 형태다. UI 입력과 참조 인자 지원이 필요하다.
- 일부 소스는 갈무리끝으로 앱 기능을 제어한다.
- 보내기는 호출마다 줄바꿈하지 않는다. 문자열 조각과 정수보내기를 합쳐 마지막 |에서 마무리한다. 연속 ||와 선행 |도 보존해야 한다.
- 전송 문자열에 $D/$T, $#155=... 같은 별도 확장 문법이 있다. 의미를 검증하거나 미지원 진단을 해야 하며 무조건 원문 전송해서는 안 된다.
- NO_SKILL.H의 지연(500) 주석은 5초다. 10ms 단위의 강한 근거지만 실행 측정 전에는 확정하지 않는다. 제한글마중의 단위 역시 따로 검증한다.
- 함수가 서로 호출하며 사냥 루프로 돌아오는 코드가 있으므로 호출 스택/재귀, 중단, 대기 이벤트 취소를 고려해야 한다.

## 5. 도움말이 밝혀준 것과 못 밝혀준 것
`tmr_y.chm`, `종합매뉴얼.chm`, 하위 폴더의 `tmr_y.chm`은 SHA256 221214CA68D489582A90B65E59935B7850BBD9B1C3B3ACF0D827B8AC2CDAC059로 동일하다. CHM에서 HTML 76개와 이미지 63개를 추출했다. 내용은 게임 배경, 속성/축복, 사냥 지역, 임무 등이며 추출된 HTML의 혼잣말/찾을글/제한글마중 검색에서는 해당 설명을 찾지 못했다.

61쪽 PDF 매뉴얼은 텍스트 레이어가 없는 이미지 문서다. 첫 6쪽 이미지와 목차를 확인했으며 게임 기초·지역·임무 중심이다. 전체 61쪽 OCR은 하지 않았으므로 전체 문서에 언어 설명이 없다고 단정하지 않는다. 지도 PDF 2개는 텍스트 추출을 확인했고 관련 키워드는 없었다.

평타/스킬 사냥 README들은 조합형 저장 방식과 설정값을 설명한다. 상세 원본 언어 매뉴얼 script.chm은 독립 파일 및 ZIP 파일 목록에서 발견하지 못했다. KSR 설치 아카이브는 헤더 문자열에서 IYAGI.CHM/HLP를 확인했지만 내부 압축 해제 전체 분석은 하지 않았다.

## 6. 구현 순서에 대한 수정 권고
1. 형식 판별 → 문서형/조합형/CP949 가져오기 → UTF-8 내부 소스 및 원본 줄 번호 유지.
2. 버전 보존 include 해석과 파서. 101개 고유 소스를 구문 테스트 자료로 사용하되 모든 파일이 원래부터 정상이라는 가정은 하지 않음.
3. 평타 공통 헤더부터 변수/배열/함수/참조 문자열 처리 구현.
4. 부분 송신 및 찾을글 계열 이벤트 상태, 시간 함수 구현.
5. 원본과 모의 서버로 비교: 백틱/공백, 감지 순서, 버퍼 정리, 시간 단위, 줄바꿈, 예약 $ 문법.
6. V1.0/V1.1 스킬 사냥과 입력 대화상자 등 기능 확대.
7. Worker 기반 실행/일시정지/중지, 오류 위치, 자원 상한과 연결 종료 취소 검증.
8. 기존 바이너리만 있는 파일의 SCF VM 호환은 별도 단계.

## 산출물과 한계
- script-inventory.json: 원본 경로, 크기, SHA256, 형식 분류. 원문 전체를 보고서에 복사하지 않음.
- corpus-static-analysis.json: 중복 제거 정적 함수/include/구문 후보 목록. 정규식 기반으로 함수 선언/사용자 함수 구분에는 한계가 있음.
- pdf-keyword-check.json: PDF 텍스트 추출 및 키워드 확인 결과. 이미지 PDF의 0건은 부재의 증거가 아님.
- .tools의 연구용 추출물은 앱 실행 엔진이 아니며 원본을 실행하지 않음.

소스 기반 호환 구현 가능성은 이전보다 명확해졌다. 그러나 아직 번역기를 구현·실행하지 않았으므로 '101개가 모두 실행된다' 또는 특정 호환율을 제시할 근거는 없다.
